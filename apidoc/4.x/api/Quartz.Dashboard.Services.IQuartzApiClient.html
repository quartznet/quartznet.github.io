Interface IQuartzApiClient

Namespace
Quartz.Dashboard.Services

Quartz.Dashboard.dll

The data source behind the dashboard's pages: either the schedulers in this process or a Quartz HTTP API somewhere else.

public interface IQuartzApiClient

Remarks

This is the dashboard's own projection of the HTTP API, not the wire contract itself — it is shaped for the pages that read it, and it is public so that an application can replace it. It speaks Quartz's vocabulary throughout: TriggerState and SchedulerStatus rather than strings, JobKeyDto and TriggerKeyDto rather than loose group/name pairs, PagedQuery's Skip/Take with PagedResult<T> rather than a paging model of its own, and ITrigger, ICalendar and JobDataMap rather than JSON.

The verbs are IScheduler's own, spelled the same way: an operation this interface forwards carries the name the scheduler gives it — Start(string, CancellationToken), Interrupt(string, JobKeyDto, CancellationToken), one TriggerJob(string, JobKeyDto, JobDataMap?, CancellationToken) with an optional map, and the Query* family for the paged listings. Only what has no counterpart on IScheduler — the scheduler listing, the execution history — names itself.

A mutation that can find nothing to act on answers with the scheduler's own bool: whether it applied. Every such member reports it, because a name shared with IScheduler that dropped the answer would read as the same operation and quietly not be one — and a page cannot tell "deleted" from "was already gone" without it.

A trigger and a calendar arrive as themselves because Quartz already owns the polymorphism they need: the serializer registry maps each kind to its own serializer, custom kinds an application registered included, and the wire format is that discriminated shape. A DTO family of the dashboard's own would have to be extended for every trigger kind and would still not describe a kind it had never heard of.

Missing things. Every member that takes a schedulerName raises KeyNotFoundException when no scheduler goes by that name, and the four members that return the thing itself rather than a listing — GetScheduler(string, CancellationToken), GetJobDetail(string, JobKeyDto, CancellationToken), GetTrigger(string, TriggerKeyDto, CancellationToken) and GetCalendar(string, string, CancellationToken) — raise it again when the thing is gone. Their return types are non-nullable, so there is no other answer available to them, and the dashboard's error boundary renders that exception as the "not found" page. A replacement that answered null! instead would fault the page with a NullReferenceException somewhere further in.

Things this data source cannot report. A capability the source does not have is a value, not an exception: GetExecutionLimits(string, CancellationToken) answers CannotReport where the underlying scheduler refuses with NotSupportedException, because "this source cannot say" and "nothing is limited" are different facts and the overview draws them differently.

Additivity. This interface is frozen from 4.0.0-beta.1 in the sense the release promises: a member added to it in 4.x arrives as a default interface member, so an implementation of an application's own keeps compiling. Its default body reports the datum as unavailable the way CannotReport does, rather than inventing one.

QueryUpcomingFires(string, DashboardUpcomingFiresQuery, CancellationToken)

Every fire of every trigger in [From, To), earliest first, computed where the scheduler's triggers are stored, with calendars applied. At most Take fires, and a window of at most 7 days within the next 30.

ValueTask<UpcomingFiresDto> QueryUpcomingFires(string schedulerName, DashboardUpcomingFiresQuery query, CancellationToken cancellationToken = default)

Parameters

schedulerName string

The scheduler whose triggers to list the fires of.

query DashboardUpcomingFiresQuery

The window, the trigger group filter and the most fires to answer.

cancellationToken CancellationToken

The cancellation instruction.

Returns

ValueTask<UpcomingFiresDto>

Remarks

What the Agenda page reads, once per load, change or Refresh. Every trigger due before the window ends is listed, in any state, so a paused trigger's fires are listed with its state. Each trigger's schedule advances from its next fire time, in its own time zone, less what its calendar excludes. A simple trigger that measures its interval from completion lists only its next fire. The fires are the schedules' times: no misfire handling, blocking, execution-group limit or standby is simulated.

A window that does not end after now, is longer than 7 days or ends more than 30 days ahead, a Take outside 1 to 1,000, or more than 10,000 triggers due before the window ends raises ArgumentException with the reason. Over HTTP and through an agent it is the …/triggers/upcoming-fires route; a host older than 4.9 has none, and the fires are computed in this process from the triggers and calendars it answers with.

A default interface member, added in 4.9. The default reports the datum as unavailable with NotSupportedException, and the Agenda says so. It does not compose the answer from GetTrigger(string, TriggerKeyDto, CancellationToken), which would be a read per trigger.

UpdateTriggerDetails(string, TriggerKeyDto, TriggerDetailsUpdate, CancellationToken)

Edits the trigger in place, as UpdateTriggerDetails(TriggerKey, TriggerDetailsUpdate, CancellationToken) does: only what update names changes, and the fire times and the state are kept. Returns true when the trigger existed and was updated, false when there was nothing to update.

ValueTask<bool> UpdateTriggerDetails(string schedulerName, TriggerKeyDto triggerKey, TriggerDetailsUpdate update, CancellationToken cancellationToken = default)

Parameters

schedulerName string

The scheduler holding the trigger.

triggerKey TriggerKeyDto

The trigger to edit.

update TriggerDetailsUpdate

What to change. See TriggerDetailsUpdate.

cancellationToken CancellationToken

The cancellation instruction.

Returns

ValueTask<bool>

Remarks

What the Trigger Detail page's editor saves through. A refusal by the scheduler — a calendar it does not hold, a misfire instruction of another family, an overlap policy for a trigger type that cannot carry one — arrives as the exception the scheduler raised, and the page shows its message beside the fields.

A default interface member, added in 4.3. The default reports the operation as unavailable with NotSupportedException: nothing else on this interface edits a trigger without replacing it, so it cannot be built out of the other members, and the page disables its editor with the reason rather than pretending.
