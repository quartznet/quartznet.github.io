Publishing Trimmed and Native AOT

A trimmed publish removes code the application does not reach; native AOT compiles the trimmed result into an executable that needs no installed runtime. Both need everything used at run time to be visible in IL. Quartz's position:

  • Quartz and seven side packages declare IsAotCompatible. Each is published by ILCompiler and run on every pull request.
  • Every other shipped package declares whether it is trimmable.
  • A job type arriving as a string resolves from the types you registered. The reflective fallback is a feature switch, off in a trimmed publish, and so are the flat quartz.* keys that name a component and job data converted through TypeConverter.
  • A trimmed publish reports no warning against Quartz.

Deciding whether to try: what Quartz claims. Ready to publish: the recipe.

What Quartz claims

<IsTrimmable>true</IsTrimmable> neither promises that nothing reflects nor decides whether Quartz is trimmed. Under TrimMode=full (default for console apps since .NET 7 and the Web SDK since .NET 8) every assembly is trimmed member by member; under TrimMode=partial an unmarked assembly is copied whole. What the mark always changes is which warnings you see:

  • A trimmer collapses a PackageReference assembly's warnings into one IL2104: Assembly 'X' produced trim warnings (TrimmerSingleWarn, true by default).
  • IL2026 (calling a [RequiresUnreferencedCode] API) is not collapsed for an assembly marked IsTrimmable. You see each of Quartz's "this API needs reflection" messages, plus one line for the rest.

A quiet build is not necessarily safe. To see everything:

<TrimmerSingleWarn>false</TrimmerSingleWarn>

<IsAotCompatible>true</IsAotCompatible> claims only that nothing needs code generated at run time: no IL3050. It turns on IsTrimmable and the trim, AOT and single-file analyzers. It does not claim that no IL2xxx remains.

Eight packages declare it, and only those: each is referenced by a canary that is published natively and run on every pull request, and whose native publish reports no warning against any Quartz package. The table below names the canary for each. To list dependencies that have not declared it:

<VerifyReferenceAotCompatibility>true</VerifyReferenceAotCompatibility>

It reports IL3058 per referenced assembly without IsAotCompatible metadata. Expect noise: the metadata arrived in .NET 10, and many compatible libraries do not declare it. Treat the list as things to check.

Feature switches

Three switches put Quartz's reflection behind a setting. PublishTrimmed and PublishAot turn all three off through the targets file in the Quartz package; nothing else changes.

Quartz.LegacyComponentKeys.IsSupportedQuartzLegacyComponentKeysSupporta flat quartz.* key that names a component by type, or sets its properties by string, fails AddQuartz naming the code form

[QuartzJob] registers through the generated AddDeclaredJobs(). A name is matched as stored, with or without its version, and in its 3.x spelling. Quartz.Jobs registers nothing by itself: a trimmed application that schedules NoOpJob calls AddJobType<NoOpJob>().

Quartz's own spellings keep working with the second switch off, mapped to the type with no reflection: quartz.jobStore.type = RAMJobStore; quartz.threadPool.type = SimpleThreadPool/DefaultThreadPool; quartz.serializer.type = stj/json; quartz.scheduler.instanceId = SYS_PROP. Job data conversions

These convert with the third switch off, exactly as their TypeConverter does: under the invariant culture, hexadecimal integers after #, 0x or &h, enum names in any case and combined with commas, a blank string as MinValue for a date or a time, and an empty one as null for Nullable<T>.

To opt back in:

<PropertyGroup>
  <QuartzTypeNameResolutionSupport>true</QuartzTypeNameResolutionSupport>
  <QuartzLegacyComponentKeysSupport>true</QuartzLegacyComponentKeysSupport>
  <QuartzJobDataTypeConverterSupport>true</QuartzJobDataTypeConverterSupport>

The publish then keeps the reflection and reports IL2026 at each guarded call site in Quartz. The trimmer may still have removed what the reflection looks for; the switches exist because that is not something a warning can rule out.

A ProjectReference to Quartz needs the targets file

The switches reach a PackageReference consumer through buildTransitive. A project that references Quartz.csproj directly imports src/Quartz/buildTransitive/net10.0/Quartz.targets by path, as the canaries do. Without a setting, ILLink and ILCompiler ignore the guard and report IL2026 at every guarded call, and the publish keeps the reflection.

What still warns, and what to do about it

Nothing in Quartz warns on its own. Job data coerced onto a job property through TypeDescriptor was the last (ValueConverter's IL2026 and IL2067), and is now the third switch; the built-in conversions cover what job data carries in practice.

What is left is a decision you make at compile time, and the compiler tells you:

What names a type as textWhere you meet itWhat to do
A driver, chosen by nameUseSqlServer(connectionString) and its siblings, [RequiresUnreferencedCode]hand over the driver's factory; trimmed, the name fails at startup
A job's type, spelled as a stringJobType(string), the string → JobType cast, a schedule file, a request body, JOB_CLASS_NAMEregister the type with AddJob<TJob>() or AddJobType<TJob>(); that is what the name resolves from
The flat quartz.* keysAddQuartz(NameValueCollection), quartz.plugin.*, quartz.dbprovider.*configure in code or from appsettings.json; the value keys still bind

Retry classification reports nothing. It reads SqlError.Number, SqliteException.SqliteErrorCode and Firebird's SQLSTATE by name, and Quartz keeps each with [DynamicDependency] whenever that driver is in the application. (Earlier releases let the trimmer remove them, and a SQLite store then gave up on a busy database instead of retrying it.)

The only real work is registering job types, and AddJob<TJob>() does that.

The recipe

Register the store with the driver's factory

Quartz references no driver, so UseSqlite(connectionString) resolves the driver's connection, command and parameter types from strings. With the type-name switch off, the container fails to build with a SchedulerConfigException naming this section; with it on, the trimmer may have removed the types and the failure is Cannot instantiate type which has no empty constructor. Every Use<Db> also takes the driver's DbProviderFactory, which names nothing:

services.AddQuartz(q => q.UsePersistentStore(store =>
{
    // The driver's own factory, rather than its name. Nothing is resolved from a string, so
    // there is nothing for the trimmer to have removed.
    store.UseSqlite(SqliteFactory.Instance, connectionString);
}));

The factory creates the connection, which creates commands and their parameters. SqlClientFactory.Instance, NpgsqlFactory.Instance, MySqlConnectorFactory.Instance and the others work the same; the configuration reference lists them, including Oracle, which needs two settings a factory cannot carry.

Or take connections from a registered DbDataSource

A DbDataSource in the container (pooling, type mappers, logging, Aspire) names no type either: it hands over every connection, and Quartz reads only the type-free half of the driver's description. UseSqlite(db => db.UseRegisteredDataSource = true) still warns, because the same callback could set a connection string instead. Register it with the two calls that overload makes:

services.AddQuartz(q => q.UsePersistentStore(store =>
{
    // What UseSqlite(db => db.UseRegisteredDataSource = true) registers, as the two calls it makes.
    // The data source hands over every connection, so only the type-free half of the driver
    // description is read and nothing is resolved from a string.
    store.UseDriverDelegate<SQLiteDelegate>();
    store.UseDataSource(db =>
    {
        db.Provider = DataSourceOptions.Providers.Sqlite;
        db.UseRegisteredDataSource = true;
    });
}));

The canary runs this natively over a DbDataSource of its own, with no connection string configured.

Name job types as types

The generic registrations point the trimmer at the job type and declare what Quartz reflects over: public constructors, public properties and implemented interfaces.

services.AddQuartz(q =>
{
    // AddJob<T> declares what Quartz reflects over on a job — its public constructors, its
    // public properties and the interfaces it implements — so the trimmer keeps exactly those,
    // and the store finds the type when it reads JOB_CLASS_NAME back as a string.
    q.AddJob<ReportingJob>(job => job.WithIdentity("reporting").StoreDurably());

    q.AddTrigger(trigger => trigger
        .ForJob("reporting")
        .WithSimpleSchedule(schedule => schedule.WithInterval(TimeSpan.FromHours(1)).RepeatForever()));
});
  • Annotated: JobBuilder.Create<TJob>(), OfType<TJob>(), AddJob<TJob>(), AddJobType<TJob>(), ScheduleJob<TJob>, TriggerBuilder.Create<TJob>(). Each also registers the type by name, which is what a string — JobType(string), a schedule file, a stored row — resolves from in a trimmed publish.
  • Wrapping one in your own generic method: annotate the forwarding type parameter too; the trim analyzer says where.
  • A type the trimmed application never registers is refused by name, not found by reflection. The message says which call to add.

Declare your own job-data and input types

PublishTrimmed (implied by PublishAot) sets the System.Text.Json.JsonSerializer.IsReflectionEnabledByDefault feature switch to false. Two serializers then need metadata for a type of your own:

SerializerWritesUsed by
The store's IObjectSerializertriggers, calendars, JobDataMapsa persistent job store
IJobInputSerializeran IJob<TInput>'s inputevery store, RAMJobStore included

Quartz's source-generated contract already covers:

  • every trigger and calendar type, CronExpression, and the NameValueCollection written under useProperties;
  • JobDataMap values of the types DataMapExtensions has accessors for: string, bool, char, int, long, float, double, decimal, DateTime, DateTimeOffset, TimeSpan, Guid, Dictionary<string, string>;
  • your own trigger and calendar types, via AddTriggerSerializer<TTrigger> and AddCalendarSerializer<TCalendar>.

Anything else of your own, such as a job-data enum or an input record, needs generated metadata:

// A job data value type of this application's own, which no contract of Quartz's can name.
public enum ReportFormat
{
    Csv,
    Pdf
}

// A typed job's input: an IJob<ReportRequest> is scheduled with UsingInput(new ReportRequest(…)).
public sealed record ReportRequest(string Title, ReportFormat Format);

// The metadata the scheduler is handed. Only a trimmed or native AOT publish needs it: with reflection
// on, the resolver chain still ends in reflection and this changes nothing.
[JsonSourceGenerationOptions(GenerationMode = JsonSourceGenerationMode.Metadata)]
[JsonSerializable(typeof(ReportFormat))]
[JsonSerializable(typeof(ReportRequest))]
internal sealed partial class ReportJsonContext : JsonSerializerContext;

Hand it to the scheduler once. Both serializers read it:

services.AddQuartz(q =>
{
    q.UsePersistentStore(store => store.UseSqlite(SqliteFactory.Instance, connectionString));

    // Once, for both serializers: the store's, which writes job data, and the one that writes
    // an IJob<TInput>'s input, which every store uses.
    q.AddJsonTypeInfoResolver(ReportJsonContext.Default);
});
  • Resolvers are asked after Quartz's contract and before reflection, in the order added. For several contexts, call it once for each.
  • With reflection on it changes nothing, so configure it unconditionally.
  • Under AddQuartz("name", …) it reaches that scheduler's serializers only.
  • Job data reads a declared object back as a Dictionary<string, string> of its members; see the table below. An input comes back as its own type.
  • The store-level store.UseSystemTextJsonSerializer(r => r.AddTypeInfoResolver(…)) still works, for job data only: it does not reach inputs.
  • The HTTP API reads the container's registry instead. See System.Text.Json.

A declared job-data object reads back member by member:

Member written asReads back as
a stringthe string
a number or a booleanits JSON text: "3", "true"
nullnull
an objectits JSON text
a collectionrefused with a JsonSerializationException when the map is written, naming the entry, the type and the member

A declared collection stored as the value itself is refused the same way. Neither reaches the store.

Without the metadata, the write fails, and the message names the type and AddJsonTypeInfoResolver:

Missing metadata forFails whenException
A job-data class or recordthe job data map is written, reflection or notJsonSerializationException
A job-data enumthe job data map is writtenJsonSerializationException, wrapping System.Text.Json's NotSupportedException
An IJob<TInput> inputit is scheduled, or a stored one is read as the job runsNotSupportedException

Turning reflection back on is not a way round this

<JsonSerializerIsReflectionEnabledByDefault>true</JsonSerializerIsReflectionEnabledByDefault> does not help: the trimmer has already removed what reflection needs. In one console application the write then failed with FileNotFoundException: Could not load file or assembly 'System.Private.Uri', under TrimMode=partial as well as full. The .NET documentation lists reflection-based serializers as incompatible with trimming; use source generation.

Configuration binds as it is

No action needed. The Quartz section of appsettings.json binds to QuartzSchedulerOptions and its siblings through a compiler-generated binder, not ConfigurationBinder's reflection, so file configuration is as AOT-safe as code. (With the reflection binder, the canary published natively but silently left MaxBatchSize, ShutdownJobInterruption and the scheduler context at their defaults; this was the last IL3050.)

The flat quartz.* keys bind their values as before. A key that names a component by type, or sets a component's properties by string, is refused under trimming unless QuartzLegacyComponentKeysSupport is true; Quartz's own spellings of a store, a thread pool, a serializer and SYS_PROP are the exception. See Feature switches.

The worked example

src/Quartz.Trimming.Canary in the repository publishes both ways and runs. It checks, in order:

  1. The serializer. Asserts JsonSerializer.IsReflectionEnabledByDefault is false, then round-trips every blob a job store writes (all five trigger types, all seven calendar types plus a chained one, a JobDataMap, a NameValueCollection, a CronExpression) through SystemTextJsonObjectSerializer, reading each back as the type StdAdoDelegate asks for and comparing re-serialized payloads byte for byte.
  2. The store. Creates SQLite from Quartz's schema with UseSqlite(SqliteFactory.Instance, …) and SchemaProvisioning.Validate, schedules a job, waits for it to fire (the job type comes back out of JOB_CLASS_NAME as a string), and reads the job and trigger back through IScheduler.
  3. Weasel. Under a real IHost, UseWeaselForSqlite() creates the schema on an empty database as the host starts (Quartz.Weasel.SQLite); the store validates it, schedules, fires and reads back.
  4. A registered DbDataSource. A DbDataSource of the canary's own over SqliteConnection, registered as an application registers Npgsql's, and taken with UseRegisteredDataSource. No connection string is configured. It asserts the store's connection provider holds this data source and no connection string, provisions the schema, schedules, fires, reads back, and counts the connections the data source handed out.
  5. The binding. Builds a scheduler from an in-memory IConfiguration and reads ten values back from the components: the scheduler name, thread pool size, scheduler context, and the rest from options.
  6. The side packages. DirectoryScanJob scans a directory and finds its listener in the container by the name in its job data (Quartz.Jobs); a quartz_jobs.json and a quartz_jobs.xml each name a job's type as text, and the job fires, with the structured job history plugin listening (Quartz.Plugins); TimeZones.FindById answers an id .NET alone refuses, through UseTimeZoneConverter (Quartz.Plugins.TimeZoneConverter). The canary publishes with InvariantGlobalization for the last: with ICU present .NET converts every IANA and Windows id itself, and no id ever reaches a resolver.
  7. Retry classification. A SqliteException reporting busy or locked, wrapped the way the store wraps it, is transient; a constraint failure is not. The answer comes from SqliteErrorCode, read by name.
  8. Type names. Asserts both feature switches read false. A registered job's name resolves through the container's ITypeLoader; NoOpJob, registered with AddJobType<NoOpJob>(), resolves under its 4.x spelling and the 3.x one a database may hold; a type that exists in the executable but was never registered is refused with the TypeLoadException that names AddJob<T>() and the switch. That line is what shows reflection is off rather than unset: with it on, the runtime finds the type. Then AddQuartz over a property bag naming Quartz.Simpl.RAMJobStore builds a scheduler, and one naming a store Quartz does not ship is refused naming UseJobStore<T>().
  9. Job data. Asserts the third switch reads false. A job fires whose int, enum, Guid, TimeSpan, DateOnly, TimeOnly, Half, Int128 and UInt128 properties are set from string job data, the last five written as their own ToString writes them; a missing value for an int? is null and for a struct its zeroed default; a Version from "1.2.3" is refused with the message that names the property, both types and the switch. With the switch on, VersionConverter would have read it.
  10. Application types. A record of the canary's own, declared once with AddJsonTypeInfoResolver and nowhere else, goes into a SQLite store as job data and comes back as its members, and as an IJob<TInput> input comes back as itself. An input type nothing declared is refused naming the call.

src/Quartz.Trimming.Canary.Wire does the same for the three packages that put a scheduler on a wire. One process serves a scheduler with Quartz.AspNetCore on Kestrel, drives it with Quartz.HttpClient over loopback, and dials a second scheduler out through Quartz.Dashboard.Agent to a hub on the same Kestrel. Each step is a round trip:

StepWhat it does over HTTP
metadatareads the scheduler's name, status and job store
scheduleschedules a job with a cron trigger
read-backreads the job, its data, the trigger and the group listing
not-foundreads a missing job as null, from a 404 with problem details
events-openopens the server-sent event stream and waits until it is live
pause, resumechanges the trigger's state and reads it back
triggertriggers the job with extra data and waits for it to run on the server
eventsreads the pause, the resume, the firing and the execution off the stream
historylists the execution, then reads it back alone with its captured log
statisticscounts the run in buckets of a day
deletedeletes the job, and its trigger with it
newer-hostreads a listing carrying names this client has no member for

Its host calls AddJobType<TJob>() for the job the client names, which is what a trimmed host serving the API has to do for every job type a caller may send.

The agent half speaks the dashboard agent protocol against a hub the canary carries, because the real hub lives in Quartz.Dashboard, which is not trimmable. The hub uses the protocol's own records, so the payloads cannot drift from what a dashboard sends:

Reading the warnings your own publish reports

A trimmed publish with the switches off reports nothing against Quartz.

With a switch set back to true, the publish reports IL2026 at each call site it guards. That is the reflection the setting chose to keep:

Property set to trueReported against
QuartzTypeNameResolutionSupportSimpleTypeLoader, JobType, BuiltInDbMetadataFactory, ValueConverter

QuartzJobDataTypeConverterSupportValueConverter
  • Warnings are about reachability. Everything in the closure is analysed, whether or not your configuration reaches it; the switches are what take the unreachable half out of the closure.
  • Warnings are not failures, and failures may not warn. What breaks a trimmed app is a removed type, found at run time. Both real bugs found in this work passed a successful publish; one broke every persistent store in every trimmed application with no new warning. That is why the canary runs.
  • Report any warning naming a Quartz member with the switches off. Quartz records none, and every pull request checks that.

What remains is #3341: the reflection in the drivers themselves, which is not Quartz's to record. It is why IsAotCompatible is the narrow claim.

The two packages that are not trimmable

Quartz.Serialization.Newtonsoft and Quartz.Dashboard declare IsTrimmable=false, in the csproj and on nuget.org.

  • Newtonsoft: Json.NET reflects over types and has no source-generated form. Marked trimmable, it would let the trimmer remove members a job data map is deserialized into, failing when a job fires. Use the default System.Text.Json serializer, built into Quartz.
  • Dashboard: Blazor Server sets [Parameter] properties by name and finds pages by type, and the Blazor packages are not trimmable either. A trimmed application drives its schedulers over the HTTP API instead; Quartz.AspNetCore and Quartz.HttpClient are trimmable.

The claim is cheap when a stored name is resolved against a compile-time table, and expensive when it is a type name. JOB_CLASS_NAME is a persisted contract that cannot change without breaking existing databases, so Quartz keeps the name and changes what answers it: the types you registered, which is a table like TickerQ's filled at startup rather than at compile time. It claims no runtime code generation, reports the one reflective call site left, and runs a real store from a native executable on every pull request.

Json.NET upstream also runs the trim and AOT analyzers without setting either flag, so no IsTrimmable metadata reaches consumers who publish with TrimMode=partial. Quartz 3.x makes no statement: EnableTrimAnalyzer is commented out in its csproj. See the migration guide.
